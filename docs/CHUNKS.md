# Полная карта: контракт чанков

Город целиком — 24 × 23 км вместо нынешних 5 × 5. Всё сразу в память браузера
не влезает, поэтому мир режется на квадраты и грузится вокруг игрока.

## Охват

```
BBOX_CITY = { south: 44.48, west: 33.35, north: 44.69, east: 33.65 }
```

Северная сторона (Радиогорка, Северный), Инкерман, Балаклава, Камышовая и
Казачья бухты, мыс Херсонес, Фиолент. В локальных метрах от ORIGIN
(площадь Нахимова, 44.6166 / 33.5254):

```
x ∈ [-13906, +9899]   (запад → восток)
z ∈ [ -8151, +15168]  (север → юг)
```

Плюс **коридор трассы Севастополь — Ялта**: полоса ±1500 м вокруг осевой
Южнобережного шоссе и отдельный квадрат самой Ялты (`BBOX_YALTA`) — город
коридором не описать.

Осевая лежит в `data/route-yalta.json`: это **реальная геометрия дороги из
OSM** (67К-1, 35А-002, 35К-022), прорежённая до шага 150 м, 655 точек.
Снимать её по памяти нельзя, и это проверено: осевая, написанная списком
посёлков (Гончарное — Ласпи — Форос — Симеиз — Алупка — Гаспра), оставила
**половину точек шоссе вне коридора**, худший промах — 4657 метров. С реальной
геометрией вне коридора не осталось ни одной из 6454 точек, худшее отклонение
171 м. `distToRoute` меряет расстояние до ближайшей точки осевой через
километровую сетку — 870 тысяч проверок в секунду, звать можно свободно.

Итого мир **не прямоугольный**: это объединение трёх областей, и между
городом и Ялтой тянется нитка чанков шириной три километра и длиной 50.
Крайняя восточная точка — Ялта, x ≈ +51 000 м; южная — Форос, z ≈ +24 000 м.
Проверка принадлежности — `inWorld(lat, lon)` из `tools/config.mjs`.

## Проекция: длина градуса долготы зависит от широты

Была ошибка, невидимая на пяти километрах центра и вылезающая на трассе.
Длина градуса долготы считалась ОДИН раз, по широте Нахимова. Ялта на 13 км
южнее, там градус длиннее на 0.2% — точка уезжала на **106 метров**, и дороги
ЮБК сошли бы со своего склона: рельеф приходит из тайлов с правильной
привязкой. Теперь масштаб долготы берётся по широте точки (`mPerDegLon(lat)`).

Обратимость сохранена — широта восстанавливается из `z` независимо от `x`,
а зная широту, знаем и масштаб долготы (`unproject`). Внутри прежнего центра
сдвиг от правки меньше метра, ручные правки домов не разъезжаются.

**Источник истины — `tools/config.mjs`.** Браузерный код его не импортирует,
поэтому в `web/js/terrain.js` формула продублирована осознанно; менять надо
в обоих местах.

## Сетка

Чанк — **1024 × 1024 м**. Индекс `cx = floor(x / 1024)`, `cz = floor(z / 1024)`.
Клеток в габаритном прямоугольнике много, но НЕПУСТЫХ заметно меньше: море,
горы и лес пусты, а вдоль трассы занята одна клетка из десяти. Поэтому список
чанков строится по фактическим данным, а не перебором bbox — это не
оптимизация, а единственный работающий способ.

Имя файла: `data/chunks/<cx>_<cz>.json`, где отрицательные пишутся с минусом:
`chunks/-3_5.json`.

## Манифест `data/chunks/index.json`

```jsonc
{
  "v": "<hash сборки>",
  "chunk": 1024,
  "meta": { "origin": {...}, "scale": {...}, "bbox": {...}, "bounds": {...} },
  "chunks": [
    { "cx": -3, "cz": 5, "n": { "buildings": 210, "roads": 44 }, "bytes": 84213 }
  ],
  "far": "far.json"
}
```

В списке только НЕПУСТЫЕ чанки. Рантайм не должен ходить за 404.

## Формат чанка

Те же поля, что в нынешнем `world.json`, но только объекты этого чанка:

```jsonc
{
  "cx": -3, "cz": 5,
  "buildings": [...], "roads": [...], "areas": [...], "green": [...],
  "water": [...], "rail": [...], "coast": [...],
  "junctions": [...], "crossings": [...], "fuel": [...], "places": [...],
  "furniture": { "stops": [...], "benches": [...], ... },
  "landmarks": [...]
}
```

**У каждого объекта обязательно поле `id`** — стабильный идентификатор (OSM id,
а для производных — `<osmid>:<индекс>`). Объект, попадающий в несколько чанков
(длинная дорога, большое здание на границе), кладётся в КАЖДЫЙ из них целиком;
рантайм дедуплицирует по `id` и строит его один раз, вместе с первым из чанков.

Принадлежность: объект попадает в чанк, если его bbox пересекает квадрат чанка,
расширенный на 64 м (запас, чтобы дорога не обрывалась ровно на шве).

## Дальний слой `data/chunks/far.json`

Весь город разом, но дёшево: контуры зданий с высотой (без имён, вывесок,
балконов), магистрали (`c <= 2`), вода, берег, крупная зелень. Цель — **≤ 3 МБ**.
Из него строится силуэт за пределами радиуса детальной загрузки, чтобы город
не обрывался в туман на 2 километрах.

Формат зданий в far: `{ "id", "poly": [x,z,...], "h" }` — и всё.

## Рельеф

* `data/terrain/index.json` — метаданные сетки чанков высот.
* `data/terrain/<tx>_<tz>.bin` — **Int16, высота в дециметрах** (÷10 = метры),
  на чанк 1024 м при z14 это ~150 × 150 отсчётов плюс кайма в 1 пиксель с
  каждой стороны (иначе на шве между чанками рвётся нормаль).
* `data/terrain/coarse.bin` — весь охват на z11 (~54 м/пиксель, Float32).
  Это фолбэк: `heightAt` обязан вернуть высоту в ЛЮБОЙ точке охвата сразу,
  даже если детальный чанк ещё не приехал.

## Рантайм: `web/js/chunks.js`

```js
export class ChunkManager {
  constructor(base, { chunk = 1024, radius = 2600, keep = 3600 })
  async init()                 // грузит index.json и far.json
  update(x, z)                 // вызывать каждый кадр; ставит очередь загрузки
  set onBuild(fn)              // fn(chunkData, key) → THREE.Group | null
  set onDrop(fn)               // fn(group, key) — снять со сцены и освободить
  get pending()                // сколько в очереди — для HUD
}
```

Правила:

* Загрузка и парс — в Web Worker, чтобы кадр не замирал на 300 мс.
* За кадр строится **не больше одного** чанка: сборка геометрии синхронна,
  и три чанка подряд дают заметный рывок.
* Чанк выгружается, когда игрок дальше `keep` (гистерезис: `keep > radius`,
  иначе на границе чанк дёргается «загрузился — выгрузился»).
* `geometry.dispose()` при выгрузке обязателен. Материалы общие, их не трогаем.

## Что НЕ меняется

Проекция, ORIGIN, система координат, направление осей — всё как было.
Существующие ручные правки (`houses.json`, `zones.json`, `landmarks.json`,
`places.json`) остаются в тех же файлах и применяются сборщиком до нарезки.
